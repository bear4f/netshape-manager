# peertune

面向**一群**客户端的 TCP 观测与调优。同仓库里的 `netshape-manager.sh` 面向的是**一个**客户端。

## 为什么要单独做一个

netshape 的模型是「一个 RTT + 一个单连接上限」，前提是客户端 = 一台固定容量的家宽设备。在那个前提下它是对的：把单流压在家宽以下，重传就下来了。

但当客户端变成一群——你自己的 5G、家里的宽带、其他地区的朋友——两个前提同时不成立：

- **RTT 不是一个数。** 同一时刻不同运营商能差 2-3 倍，晚高峰再翻一倍，5G 还会因为调度和换手在几秒内来回跳。
- **容量不是一个数。** 500M 家宽和峰值 200M 且剧烈波动的 5G，差一个数量级。

对一个分布，你没法取一个点来调。所以 peertune 换了做法：**把分布显示出来，把全局边界设安全，不设单流上限。**

## 装与用

```bash
sudo bash peertune.sh tune      # 首次：安装自身 + 开机服务 + 应用调优
sudo peertune                   # 之后：打开面板
```

```bash
peertune scan                   # 看每个客户端的分布（核心功能）
peertune scan --group net       # 按 /24 聚合，一个人多设备时更好看
peertune scan --samples 8 --interval 5
peertune tune --coverage-rtt 250 --port 1000 --total 0
peertune doctor                 # 拥塞控制版本、队列类型、与 netshape 的冲突
peertune status
peertune uninstall              # 按快照还原内核参数
```

> peertune 和 netshape 都会接管 root qdisc 和 sysctl drop-in。同时装等于谁最后跑谁生效，而且两边面板都会显示自己那一套，看不出真实状态。`tune` 检测到 netshape 会直接中止并让你先卸载它。

## `scan`：这是分布，不是一个数

```
  客户端                  连接  RTT50  RTT95   最低   抖动   膨胀    重传%
──────────────────────────────────────────────────────────────────────
  198.51.100.78               1  174.1  274.2   50.0  0.379   3.48   0.0947
    排队膨胀 ｜ 剧烈抖 ｜ 干净 ｜ bbr ｜ 中位 48.0 Mbps ｜ cwnd 38
    → 接入网排队膨胀（典型 5G/家宽上行）——瓶颈队列不在你的服务器上，
      服务端限速无效，靠 BBRv3 或降 pacing
  192.0.2.40                  1  161.9  169.2  158.0  0.031   1.02   3.3023
    队列健康 ｜ 稳 ｜ 丢包重 ｜ bbr ｜ 中位 85.0 Mbps ｜ cwnd 22
    → 路径丢包或限速器——重传高但没有排队，降单流速率有用
  203.0.113.5                 1   31.1   32.8   31.0  0.039   1.00   0.0062
    队列健康 ｜ 稳 ｜ 干净 ｜ bbr ｜ 中位 400.0 Mbps ｜ cwnd 140
    → 健康
```

数据来自 `ss -tin`，按连接采样多次后聚合。三个关键指标：

| 指标 | 算法 | 判读 |
|---|---|---|
| **膨胀** | `RTT50 / 该路径最低 RTT` | `<1.5` 队列健康，`>3` 对端接入网在囤队列 |
| **抖动** | `rttvar / RTT50` | `<0.1` 稳，`>0.3` 无线链路的典型特征 |
| **重传%** | 采样窗口内的**增量** | `<0.1` 干净，`>1` 丢包或限速器 |

**膨胀是这里最有用的一个。** `minrtt` 是内核记录的这条路径的物理下限，`rtt` 是当前平滑值；两者的比值就是队列涨到了路径底噪的几倍。5G 下行的基站缓冲极深，一旦 BBR 灌进去，膨胀会到 3-5 倍——这时你看到的"速度波动"其实是 RTT 在波动。

三个指标**组合起来**才有诊断价值：

- 膨胀高 + 重传低 → 接入网在排队。**瓶颈队列不在你的服务器上，服务端限速无效。**
- 重传高 + 膨胀低 → 路径丢包或限速器。降单流速率有用。
- 重传高 + 膨胀高 → 多半打穿了限速器。
- 只有抖动高 → 无线调度/换手。速率波动来自这里，不是你的配置。

重传率取的是**采样窗口内的增量**（按连接算首末差值），不是连接生命周期的平均——一条连接一小时前抖过一次，不代表它现在有问题。

## 为什么没有「单连接限速」

客户端容量差一个数量级时，任何一个固定数字都是错的：

- 设 430（按 500M 家宽）→ 对峰值 200M 的 5G **永远不触发**，等于没设。BBR 继续自由探测，继续把基站缓冲灌满。
- 设 200（按 5G）→ 把 500M 家宽那台限死了。

peertune 用 **CAKE `dual-dsthost`** 代替：按客户端公平 + COBALT AQM，不需要知道任何一个客户端的速率——它约束的是**队列**，不是速率。没有 CAKE 时依次退到 `fq_codel`（有 AQM，无按客户端公平）和 `fq`（只有 pacing）。

不设 `bandwidth` 时 CAKE 不整形，但**主机隔离和 AQM 仍然工作**，这正是瓶颈在远端时想要的。要保护自己的端口再加 `--total`。

## 为什么覆盖 RTT 不去实测

缓冲上限同时也是 in-flight 上限，所以它必须覆盖你服务的**最远**那个客户端。按实测值定是个陷阱——一次测量只是分布里随机的一个点。

代价是不对称的：

- **估高**：只多付一点 BBR 超发。
- **估低**：变成一个**查不出来的硬天花板**，用户怎么测都上不去，还找不到原因。

实测一下差多少（1G 端口，4G 内存）：

| 覆盖 RTT | 缓冲上限 |
|---|---|
| 40 ms | 8 MiB（撞下限） |
| 150 ms | 36 MiB |
| 250 ms（默认） | 60 MiB |

默认 250ms 覆盖：优化线 40-70ms｜香港 ~145ms｜美西 160-180ms｜欧美 230-250ms｜晚高峰 300ms+。

上限之外还有两道约束：单个 socket 不超过全局 `tcp_mem` 预算的 1/8（保证至少容得下 8 条大流），绝对不超过 256 MiB。

这个论证来自 [tcpfit](https://github.com/Kylin010/tcpfit) —— 它一开始 ping 五个国内 DNS 取中位数，后来把整套 RTT 测量删掉改成硬编码，理由写得很清楚：anycast 污染、ICMP 不通、以及最根本的「到中国的 RTT 不是一个数」。

## 拥塞控制：优先 BBRv3

BBRv1 的带宽估计是约 10 个 RTT 的**最大值滤波**——无线链路一变差，它还抱着旧的高估值继续超发好几秒。这在 5G 上就是"好一阵卡一阵"的直接来源。v2/v3 会响应丢包和 ECN，温和得多。

`peertune` 按 `bbr3 > bbr2 > bbr > cubic` 选择。注意 **XanMod 等发行版直接把 BBRv3 装成 `bbr`**，所以内核只报 `bbr` 时看不出版本，`peertune doctor` 会提示怎么确认：

```bash
modinfo tcp_bbr 2>/dev/null | head -3
```

想要 v3 而当前内核只有 v1，只能换内核，peertune 不会替你装。

## 说清楚做不到什么

**运营商基站的 bufferbloat 从服务端修不了。** 膨胀 4 倍那一行的意思就是"队列在别人家里"。能做的只有别灌那么快（pacing + BBRv3），以及别在服务端再叠一层队列。

5G 上看片卡顿，**客户端播放器的缓冲长度比服务端调优管用得多**。peertune 的价值是让你知道卡在哪一层，而不是假装能修好每一层。
